3.1MapReduce workflows@@s3-1@@

🗣 In simple words
Finding the max temperature needed only one MapReduce job. Harder problems are solved by chaining several simple jobs — the output of one job becomes the input of the next — instead of writing one very complicated job.
  • When processing gets more complex, the complexity is generally shown by having more MapReduce jobs, rather than more complex map and reduce functions.
  • Rule of thumb: think about adding more jobs, rather than adding complexity to jobs.
  • For more complex problems, consider a higher-level language than MapReduce: PigHiveCascadingCrunchSpark. Benefit: they translate your work into MapReduce jobs for you, so you can concentrate on the analysis.

Decomposing a problem into MapReduce jobs

📌 Goal
Find the mean maximum temperature for every station + day/month across many years. E.g., for station 029070-99999 on January 1: take the max temperature on Jan 1 1901, Jan 1 1902, … Jan 1 2000, then take the mean of those maxima.
Figure 3.1 — Key idea: complex problem → break into multiple MapReduce jobs

JobControl — running jobs in the right order

  • With multiple MapReduce jobs, they must be executed in the correct order.
  • If jobs form a linear chain (Job 1 → Job 2 → Job 3), run them one after another:
    JobClient.runJob(conf1) runs the first job; JobClient.runJob(conf2) runs the second only after the first finishes successfully. If a job fails, runJob() throws an IOException, so later jobs are not executed.
  • For more complex workflows, jobs may form a DAG (Directed Acyclic Graph) with different dependencies. JobControl is used to manage such workflows. It:
    • stores the jobs,
    • defines dependencies between jobs,
    • runs jobs in the correct dependency order,
    • monitors job progress,
    • provides job status and error information,
    • does not run dependent jobs if a required job fails.

3.2Writing a unit test with MRUnit@@s3-2@@

🗣 In simple words
Before running on a real cluster, we test the mapper and reducer on their own: give them a known input, and check they produce the expected output. MRUnit is the tool that does this.
  • Map and reduce functions are easy to test in isolation — a consequence of their functional style.
  • MRUnit is a testing library that makes it easy to pass known inputs to a mapper or reducer and check that the outputs are as expected.
  • MRUnit is used with a standard test framework such as JUnit, so you can run tests in your normal development environment.
  • If the expected output values are not emitted, MRUnit fails the test.

Testing the Mapper — MapDriver

We use MRUnit's MapDriver, configured with the mapper under test (MaxTemperatureMapper), the input key and value, the expected output key (a Text for the year 1950) and expected output value (an IntWritable −11, i.e., −1.1 °C), then call runTest().

@Test
public void processesValidRecord() throws IOException, InterruptedException {
  Text value = new Text("0043011990999991950051518004+68750+023550FM-12+0382" +
                                   // Year ^^^^
      "99999V0203201N00261220001CN9999999N9-00111+99999999999");
                                   // Temperature ^^^^^
  new MapDriver<LongWritable, Text, Text, IntWritable>()
    .withMapper(new MaxTemperatureMapper())
    .withInput(new LongWritable(0), value)
    .withOutput(new Text("1950"), new IntWritable(-11))   // expected (year, temp)
    .runTest();
}

Testing the Reducer — ReduceDriver

Give the reducer a key (1950) and a list of values (10, 5); verify it outputs the largest (10).

@Test
public void returnsMaximumIntegerInValues() throws IOException, InterruptedException {
  new ReduceDriver<Text, IntWritable, Text, IntWritable>()
    .withReducer(new MaxTemperatureReducer())
    .withInput(new Text("1950"),
        Arrays.asList(new IntWritable(10), new IntWritable(5)))
    .withOutput(new Text("1950"), new IntWritable(10))       // max of 10 and 5
    .runTest();
}

Running a job in a local job runner (testing the whole job)

Using the Tool interface, we write a driver (MaxTemperatureDriver extends Configured implements Tool) and test it with a local, in-process job runner on a small amount of known data:

@Test
public void test() throws Exception {
  Configuration conf = new Configuration();
  conf.set("fs.defaultFS", "file:///");                 // use the local filesystem
  conf.set("mapreduce.framework.name", "local");       // use the local job runner
  conf.setInt("mapreduce.task.io.sort.mb", 1);
  Path input = new Path("input/ncdc/micro");
  Path output = new Path("output");
  FileSystem fs = FileSystem.getLocal(conf);
  fs.delete(output, true);                                 // delete old output
  MaxTemperatureDriver driver = new MaxTemperatureDriver();
  driver.setConf(conf);
  int exitCode = driver.run(new String[] { input.toString(), output.toString() });
  assertThat(exitCode, is(0));
  checkOutput(conf, output);                                 // compare actual vs expected, line by line
}
1 · Mapper test

Test only the mapper using MapDriver. Input: weather record (1950, −1.1 °C) → expected (1950, −11). −11 = temperature in tenths of a degree.

2 · Reducer test

Test only the reducer using ReduceDriver. Input: key 1950, values [10, 5] → expected (1950, 10).

3 · Complete job test

Run the whole job (mapper + shuffle/sort + reducer) on a local machine with a small input file using the local job runner; check the output file matches.

🧠 Memory trick
"MapDriver tests the Mapper, ReduceDriver tests the Reducer, local job runner tests the whole job." Test small pieces first → then the whole.

3.3Anatomy of a MapReduce job run@@s3-3@@

  • You can run a MapReduce job with a single method call: submit() on a Job object — or waitForCompletion(), which submits the job if not already submitted, then waits for it to finish. This one call conceals a great deal of processing behind the scenes.
  • In Hadoop releases up to 0.20, the property mapred.job.tracker determines the means of execution. If set to local (the default), the local job runner is used — runs the whole job in a single JVM, designed for testing and small datasets.
  • In Hadoop 0.23.0 a new MapReduce implementation was introduced — MapReduce 2, built on a system called YARN.
  • The framework used for execution is set by the property mapreduce.framework.name, which takes the values:

3.4Classic MapReduce (MapReduce 1)@@s3-4@@

A job run in classic MapReduce has four independent entities:

💻 Client

Submits the MapReduce job.

🧭 JobTracker

Coordinates the job run. A Java application whose main class is JobTracker.

👷 TaskTrackers

Run the tasks the job has been split into. Java apps, main class TaskTracker.

🗄 Distributed FS

Normally HDFS — used for sharing job files between the other entities.

🧠 Memory trick — MR1 entities
"C J T D" → "Client Just Talks to DFS" — Client, JobTracker, TaskTrackers, Distributed file system.
Figure 3.2 — How Hadoop runs a MapReduce job using the classic framework (Textbook Fig. 6-1). Steps 1 → 10.
A · Job submission (steps 1–4)
  • 1submit() on Job creates an internal JobSubmitter and calls submitJobInternal() on it.
  • 2Asks the JobTracker for a new job ID (getNewJobId()). Then it checks the output specification — if the output directory isn't specified or already exists, the job isn't submitted and an error is thrown. It computes the input splits — if they can't be computed (e.g., input paths don't exist), the job isn't submitted.
  • 3Copies the resources needed to run the job — the job JAR, the configuration file and the computed input splits — to the JobTracker's file system (shared FS). The job JAR is copied with a high replication factor so there are many copies across the cluster for TaskTrackers to access.
  • 4Tells the JobTracker the job is ready for execution (submitJob() on JobTracker).
B · Job initialisation (steps 5–6)
  • 5The JobTracker puts the job in an internal queue; the job scheduler picks it up and initialises it — creates an object to represent the job, encapsulating its tasks and bookkeeping information to track task status and progress.
  • 6To create the list of tasks, the scheduler retrieves the input splits computed by the client from the shared file system. It creates one map task for each split. The number of reduce tasks is set by the mapred.reduce.tasks property (set via setNumReduceTasks()). Tasks are given IDs.
C · Task assignment (step 7)
  • 7TaskTrackers run a simple loop that periodically sends heartbeat calls to the JobTracker. Heartbeats tell the JobTracker that a TaskTracker is alive, and also act as a channel for messages: the TaskTracker says whether it's ready for a new task, and if so, the JobTracker allocates a task via the heartbeat return value.
D · Task execution (steps 8–10)
  • 8The TaskTracker localises the job JAR by copying it from the shared file system to its own file system, and copies any files needed from the distributed cache to local disk. It creates a local working directory and un-jars the JAR into it.
  • 9It creates a TaskRunner, which launches a new Java Virtual Machine (JVM)…
  • 10…to run each task in — so that bugs in the user's map/reduce functions don't affect the TaskTracker (e.g., crash or hang it). (It is possible to reuse the JVM between tasks.)
🧠 Memory trick — the 4 phases
"S I A E" → Submission · Initialisation · Assignment · Execution — "Students In An Exam". Same 4 phases appear in YARN too!

3.5YARN (MapReduce 2)@@s3-5@@

🗣 In simple words
In MR1, the JobTracker did two jobs: managing cluster resources and babysitting every task of every job. On huge clusters it became overloaded. YARN splits that work: a ResourceManager manages resources for the whole cluster, and each job gets its own ApplicationMaster to babysit its tasks.
  • For very large clusters — around 4,000 nodes and higher — classic MapReduce hits scalability bottlenecks. In 2010 a group at Yahoo! began designing the next generation of MapReduce.
  • The result was YARN — Yet Another Resource Negotiator (or the recursive acronym YARN Application Resource Negotiator).
  • YARN fixes the scalability problems by splitting the responsibilities of the JobTracker into separate entities. The JobTracker handled both:
    • job scheduling — matching tasks with TaskTrackers, and
    • task progress monitoring — tracking tasks, restarting failed/slow tasks, bookkeeping such as counter totals.
  • YARN separates these into two independent daemons:
    • a ResourceManager to manage the use of resources across the cluster, and
    • an ApplicationMaster to manage the lifecycle of applications running on the cluster.
Figure 3.3 — YARN splits the JobTracker's two responsibilities into separate daemons

MapReduce on YARN involves five independent entities:

💻 Client

Submits the MapReduce job.

🧭 YARN ResourceManager

Coordinates the allocation of compute resources on the cluster.

🧑‍🔧 YARN NodeManagers

Launch and monitor the compute containers on machines in the cluster.

🎬 MapReduce ApplicationMaster

Coordinates the tasks running the MapReduce job. The AM and the tasks run in containers scheduled by the ResourceManager and managed by NodeManagers.

🗄 Distributed FS

Normally HDFS — used for sharing job files between the other entities.

🧠 Memory trick

"C R N A D" → "Can Rahul Not Attend Daily?" — Client, ResourceManager, NodeManagers, ApplicationMaster, DFS.

Figure 3.4 — How Hadoop runs a MapReduce job using YARN (Textbook Fig. 7-1). Steps 1 → 11.
A · Job submission (steps 1–4)
  • 1submit() on Job creates an internal JobSubmitter and calls submitJobInternal().
  • 2Asks the ResourceManager for a new application ID, used as the MapReduce job ID. Checks the output specification (output dir not specified or already exists → error). Computes the input splits (can't compute, e.g., input paths don't exist → error).
  • 3Copies the resources needed to run the job — job JAR, configuration file, computed input splits — to the shared file system in a directory named after the job ID.
  • 4Submits the job by calling submitApplication() on the ResourceManager.
B · Job initialisation (steps 5–7)
  • 5a5bThe ResourceManager hands the request to the YARN scheduler. The scheduler allocates a container, and the ResourceManager launches the ApplicationMaster's process there, under the NodeManager's management.
  • 6The ApplicationMaster for MapReduce jobs is a Java application whose main class is MRAppMaster. It initialises the job by creating bookkeeping objects to track the job's progress (it will receive progress and completion reports from the tasks).
  • 7It retrieves the input splits computed in the client from the shared file system.
C · Task assignment (step 8)
  • 8If the job does not qualify to run as an uber task (a small job run inside the AM's own JVM), the ApplicationMaster requests containers for all map and reduce tasks from the ResourceManager. Map task requests are made first, with higher priority than reduce tasks, since all maps must complete before the reduce's sort phase can start. Reduce requests are not made until 5% of map tasks have completed ("reduce slow start").
D · Task execution (steps 9–11)
  • 9a9bOnce a task is assigned a container on a node, the ApplicationMaster starts the container by contacting the NodeManager.
  • 10The task is executed by a Java application whose main class is YarnChild. Before running the task, it localises the resources it needs — job configuration, JAR file, and any files from the distributed cache.
  • 11Finally, it runs the map or reduce task.
💡 Progress & status updates in YARN (slide figure 7-3)
Each task (MapTask/ReduceTask inside the YarnChild) reports its progress and counters to its MRAppMaster (status update). The client polls the MRAppMaster (getJobStatus) to show progress to the user — the ResourceManager is not involved in task-level status, which keeps it light.
