2.1Distributed file systems@@s2-1@@

🗣 In simple words
When a file is too big for one computer, we cut it into pieces and store the pieces on many computers connected by a network. Software that manages files spread over many machines like this is called a distributed file system. Hadoop's one is called HDFS.
  • When a dataset outgrows the storage capacity of a single physical machine, it becomes necessary to partition it across a number of separate machines.
  • File systems that manage the storage across a network of machines are called distributed file systems (DFS). A DFS allows access to files from multiple hosts sharing via a computer network.
  • Being network-based, they are more complex than regular disk file systems.
  • One of the biggest challenges: making the file system tolerate node failure without suffering data loss.
  • Hadoop's DFS is HDFS. Hadoop can also work with other storage (the local file system, Amazon S3).
Figure 2.1 — A distributed file system

2.2The design of HDFS@@s2-2@@

Definition — learn word-for-word

HDFS is a file system designed for storing very large files with streaming data access patterns, running on clusters of commodity hardware.

📦 Very large files

Files that are hundreds of MB, GB or TB in size. Hadoop clusters today store petabytes of data.

🌊 Streaming data access

Built around write-once, read-many-times. A dataset is generated/copied once, then analysed many times. Each analysis reads a large part (or all) of the dataset, so the time to read the whole dataset matters more than the latency of reading the first record.

🖥 Commodity hardware

Doesn't need expensive, highly reliable hardware — runs on commonly available hardware from multiple vendors. Node failure is likely in large clusters, so HDFS is designed to keep working without noticeable interruption.

🧠 Memory trick
HDFS is good at "L S C" → Large files, Streaming access, Cheap (commodity) hardware.

Where HDFS does NOT work well

❌ 1. Low-latency data access

Not suitable for apps needing access in the tens of milliseconds. HDFS is optimised for high data throughput, which may come at the expense of latency. → Use HBase instead for low-latency access.

❌ 2. Lots of small files

The NameNode holds file-system metadata in memory; every file, directory and block uses memory. So the number of files is limited by NameNode memory: millions of files are feasible, billions are beyond current hardware.

Rule of thumb (textbook): each file/dir/block ≈ 150 bytes of NameNode memory.
❌ 3. Multiple writers, arbitrary file modifications

A file is written by a single writer. Writes are always made at the end of the file (append-only). No multiple writers, no modifications at arbitrary offsets.

🧠 Memory trick — HDFS weaknesses
"L S M": HDFS is not for Low latency, Small files, or Multiple writers. (Opposite of its strengths: large files, streaming, one writer.)

2.3HDFS concepts — Blocks@@s2-3@@

  • A disk has a block size — the minimum amount of data it can read or write. Disk blocks are normally 512 bytes.
  • File systems for a single disk deal with data in blocks that are an integral multiple of the disk block size — typically a few kilobytes.
  • This is usually transparent to the user, but tools like df and fsck ("file system check") work at block level.
  • HDFS also has blocks, but a much larger unit — 128 MB by default. Files in HDFS are broken into block-sized chunks, stored as independent units.
  • Unlike a single-disk file system, a file smaller than a block does not occupy a full block of storage — e.g., a 1 MB file with a 128 MB block size uses 1 MB of disk, not 128 MB.
Figure 2.2 — A 500 MB file split into 128 MB blocks, each replicated 3 times across DataNodes. Note the last block is only 116 MB.

Benefits of the block abstraction

1 · File bigger than any disk

A file can be larger than any single disk in the network — blocks don't need to be on the same disk, so they can use any disk in the cluster.

2 · Simpler storage subsystem

Making the unit a block rather than a file simplifies storage management (fixed size → easy to calculate how many fit on a disk; metadata handled separately). Simplicity matters in distributed systems where failure modes are varied.

3 · Fits replication

Blocks fit well with replication for fault tolerance and availability: each block is replicated to a small number of physically separate machines (typically three), guarding against corrupted blocks and disk/machine failure.

⚠️ Common mistake
Older textbook editions/slides may say 64 MB (Hadoop 1). Your slides say 128 MB by default (Hadoop 2+) — write 128 MB. Also: HDFS block (128 MB) ≫ normal file system block (few KB) ≫ disk block (512 bytes).

2.4NameNodes and DataNodes@@s2-4@@

🗣 In simple words
Think of a library. The NameNode is the librarian's catalogue: it knows which book (file) is made of which pages (blocks) and which shelf (DataNode) holds each page — but it doesn't hold the pages itself. The DataNodes are the shelves that actually store the pages.

An HDFS cluster has two types of nodes operating in a master–worker (master–slave) pattern: a NameNode (the master) and a number of DataNodes (workers).

👑 NameNode (master)
  • Manages the file system namespace.
  • Maintains the file system tree and the metadata for all files and directories.
  • Stored persistently on local disk as two files: the namespace image and the edit log.
  • Knows which DataNodes hold the blocks of each file (this block-location map is rebuilt from DataNode reports at startup, kept in memory).
👷 DataNodes (workers)
  • The workhorses of the file system.
  • Store and retrieve blocks when told to (by clients or the NameNode).
  • Report back to the NameNode periodically with lists of blocks they are storing (block reports / heartbeats).
Figure 2.3 — HDFS architecture: one NameNode holds metadata; DataNodes in racks hold replicated blocks; clients read/write blocks directly from/to DataNodes
🔑 Key point
Without the NameNode, the file system cannot be used. If the machine running the NameNode were destroyed, all files would be lost — there'd be no way to know how to rebuild files from the blocks on the DataNodes. So the NameNode must be made resilient to failure.

Making the NameNode resilient — two mechanisms

1 · Back up the metadata files

Back up the files that make up the persistent state of the file-system metadata. Hadoop can be configured so the NameNode writes its persistent state to multiple file systems. These writes are synchronous and atomic. Usual choice: write to local disk + a remote NFS mount (Network File System).

2 · Run a Secondary NameNode

Despite its name, it does not act as a NameNode. Its main role is to periodically merge the namespace image with the edit log to stop the edit log becoming too large. Runs on a separate machine (needs lots of CPU and as much memory as the NameNode). Keeps a copy of the merged namespace image, usable if the NameNode fails.

Figure 2.4 — The Secondary NameNode creates checkpoints by merging the namespace image (fsimage) with the edit log
⚠️ Common mistake
The Secondary NameNode is NOT a backup/standby NameNode. It only does checkpointing (merging). If the NameNode dies, the Secondary can't take over automatically — that's what the Standby NameNode in HDFS High Availability (§2.6) is for.

2.5HDFS Federation@@s2-5@@

🗣 In simple words
One librarian can only remember so many books. In a huge library, hire more librarians and give each one a section (e.g., one handles /user, another handles /share). That's federation.
  • The NameNode keeps a reference to every file and block in memory → on very large clusters with many files, memory becomes the limiting factor for scaling.
  • HDFS Federation, introduced in the 2.x release series, allows a cluster to scale by adding NameNodes, each of which manages a portion of the file system namespace.
  • Example: one NameNode manages all files under /user, a second handles files under /share.
  • Each NameNode manages a namespace volume = the metadata for the namespace + a block pool containing all the blocks for the files in that namespace.
  • Namespace volumes are independent: NameNodes do not communicate with one another, and the failure of one NameNode does not affect the availability of namespaces managed by others.
Figure 2.5 — HDFS Federation: several independent NameNodes, each with its own namespace volume (metadata + block pool)

2.6HDFS High Availability (HA)@@s2-6@@

The problem: the NameNode is a single point of failure

  • Backing up metadata to multiple file systems + a Secondary NameNode protects against data loss, but does not provide high availability.
  • The NameNode is still a single point of failure (SPOF). If it fails, all clients — including MapReduce jobs — can't read, write, or list files, because the NameNode is the sole repository of metadata and the file-to-block mapping. The whole Hadoop system is out of service until a new NameNode is online.
  • Manual recovery: an administrator starts a new primary NameNode with one of the metadata replicas and configures DataNodes and clients to use it. The new NameNode can't serve requests until it has:
    1. (i) loaded its namespace image into memory,
    2. (ii) replayed its edit log, and
    3. (iii) received enough block reports from DataNodes to leave safe mode.
    On large clusters this "cold start" can take 30 minutes or more.

The solution: an active–standby pair of NameNodes

Hadoop 2 adds HA with a pair of NameNodes in an active–standby configuration. If the active NameNode fails, the standby takes over its duties and continues servicing client requests without a significant interruption. Architectural changes needed:

1 · Shared edit log

NameNodes use highly available shared storage to share the edit log. When the standby comes up, it reads up to the end of the shared edit log to sync with the active one, then keeps reading new entries as the active writes them.

2 · Block reports to both

DataNodes must send block reports to both NameNodes, because block mappings are stored in a NameNode's memory, not on disk.

3 · Client failover

Clients must be configured to handle NameNode failover, using a mechanism that is transparent to users.

4 · Standby replaces Secondary

The Secondary NameNode's role is subsumed by the standby, which takes periodic checkpoints of the active NameNode's namespace.

Figure 2.6 — HDFS High Availability with an active–standby NameNode pair
🎯 Exam tip
Typical question: "Explain HDFS Federation and High Availability." Federation solves scaling (memory limit → more NameNodes, each owning part of the namespace). HA solves the single point of failure (standby NameNode takes over). Write problem → solution → diagram for each.

2.7Data flow — Anatomy of a file read@@s2-7@@

🗣 In simple words
To read a file, the client first asks the NameNode "where are the blocks?", then reads each block directly from the nearest DataNode, one after another. The NameNode only gives directions — the actual data never passes through it.
Figure 2.7 — A client reading data from HDFS (Textbook Fig. 3-2). Follow steps 1 → 6.
  • 1The client opens the file by calling open() on the FileSystem object, which for HDFS is an instance of DistributedFileSystem.
  • 2DistributedFileSystem calls the NameNode, using remote procedure calls (RPCs), to get the locations of the first few blocks of the file. For each block, the NameNode returns the addresses of the DataNodes that have a copy, sorted by proximity to the client (based on the cluster's network topology). DistributedFileSystem returns an FSDataInputStream (supports file seeks) to the client, which wraps a DFSInputStream that manages DataNode and NameNode I/O.
  • 3The client calls read() on the stream. DFSInputStream, which has stored the DataNode addresses for the first few blocks, connects to the first (closest) DataNode for the first block.
  • 4Data is streamed from the DataNode back to the client, which calls read() repeatedly on the stream.
  • 5When the end of the block is reached, DFSInputStream closes the connection to that DataNode, then finds the best DataNode for the next block. Blocks are read in order; DFSInputStream also asks the NameNode for the locations of the next batch of blocks as needed.
  • 6When the client has finished reading, it calls close() on the FSDataInputStream.
🔧 If a DataNode fails during reading

DFSInputStream tries the next closest DataNode for that block. It also remembers failed DataNodes so it doesn't needlessly retry them for later blocks.

🧪 If a block is corrupted

DFSInputStream verifies checksums for data transferred from DataNodes. If a corrupted block is found, it reads a replica from another DataNode and reports the corrupted block to the NameNode.

🔑 Why this design is good
The client contacts DataNodes directly to get data, and the NameNode only answers block-location requests (held in memory → very fast). This lets HDFS scale to many concurrent clients, because data traffic is spread across all DataNodes and the NameNode doesn't become a bottleneck.
🧠 Memory trick — file read (6 steps)
"Open · Get · Read · Read · Read-next · Close" → O G R R R C — "Only Good Readers Really Read Carefully".

2.8Data flow — Anatomy of a file write@@s2-8@@

🗣 In simple words
To write a file, the client asks the NameNode to create it, then sends data in small packets down a chain (pipeline) of 3 DataNodes: DataNode 1 saves and passes it to DataNode 2, which saves and passes it to DataNode 3. Acknowledgements flow back up the chain.
Figure 2.8 — A client writing data to HDFS (Textbook Fig. 3-4). Follow steps 1 → 7. Red = data packets; dark = acknowledgements.
  • 1The client creates the file by calling create() on DistributedFileSystem.
  • 2DistributedFileSystem makes an RPC call to the NameNode to create a new file in the namespace, with no blocks associated with it. The NameNode performs checks: the file doesn't already exist and the client has the right permissions. If checks pass → it records the new file; otherwise file creation fails and the client gets an IOException. DistributedFileSystem returns an FSDataOutputStream (wrapping a DFSOutputStream).
  • 3As the client writes data, DFSOutputStream splits it into packets, written to an internal queue called the data queue. The data queue is consumed by the DataStreamer, which asks the NameNode to allocate new blocks by picking a list of suitable DataNodes to store the replicas. The list of DataNodes forms a pipeline — with replication level 3, there are three nodes in the pipeline.
  • 4The DataStreamer streams packets to the first DataNode, which stores each packet and forwards it to the second; the second stores it and forwards it to the third (last) DataNode.
  • 5DFSOutputStream also keeps an internal queue of packets waiting to be acknowledged, called the ack queue. A packet is removed from the ack queue only when it has been acknowledged by all DataNodes in the pipeline.
  • 6When the client has finished writing, it calls close() on the stream. This flushes all remaining packets to the pipeline and waits for acknowledgements…
  • 7…before contacting the NameNode to signal that the file is complete.
🔧 If a DataNode fails while data is being written
  1. The pipeline is closed, and any packets in the ack queue are added to the front of the data queue, so DataNodes downstream of the failed node don't miss any packets.
  2. The current block on the good DataNodes is given a new identity, communicated to the NameNode, so the partial block on the failed DataNode will be deleted if it recovers later.
  3. The failed DataNode is removed from the pipeline, and a new pipeline is built from the two good DataNodes. The rest of the block is written to them. (The NameNode notices the block is under-replicated and arranges a further replica on another node.)
