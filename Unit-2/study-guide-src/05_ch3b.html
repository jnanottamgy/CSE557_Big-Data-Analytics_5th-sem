3.6Failures@@s3-6@@

🗣 In simple words
In a cluster of thousands of cheap machines, something is always breaking: user code crashes, a machine dies, a network link fails. Hadoop is designed to notice failures (via missing heartbeats) and retry the work elsewhere, so the job still finishes.

Failures in Classic MapReduce (MR1) — 3 failure modes

1 · Task failure
  • Most common: user code in the map/reduce task throws a runtime exception. The child JVM reports the error to its parent TaskTracker before it exits; the error ends up in the user logs.
  • The TaskTracker marks the task attempt as failed, freeing a slot for another task.
  • Streaming tasks: if the Streaming process exits with a non-zero exit code, it's marked as failed.
  • Sudden exit of the child JVM (e.g., a JVM bug): the TaskTracker notices the process has exited and marks the attempt as failed.
  • (Textbook: hanging tasks are noticed by a missing progress update after a timeout — default 10 min.)
2 · TaskTracker failure
  • If a TaskTracker crashes or runs very slowly, it stops sending heartbeats to the JobTracker (or sends them very infrequently).
  • The JobTracker notices and removes it from its pool of TaskTrackers to schedule tasks on.
  • Blacklisting: a TaskTracker can be blacklisted even if it hasn't failed. If more than four tasks from the same job fail on it, the JobTracker records a fault. It's blacklisted if its faults exceed a minimum threshold and are significantly higher than the cluster average.
3 · JobTracker failure
  • The most serious failure mode.
  • Hadoop has no mechanism for dealing with it — the JobTracker is a single point of failure — so the job fails.
  • Low chance of occurring (one particular machine failing is unlikely).
  • Good news: improved in YARN, one of whose design goals is to eliminate single points of failure.

3.7Job scheduling@@s3-7@@

🗣 In simple words
Many users share one cluster. A scheduler decides whose job gets the cluster's resources, and when — like a teacher deciding the order students use the one computer lab.

MapReduce in Hadoop comes with a choice of schedulers: the default in MapReduce 1 is the original FIFO queue-based scheduler, plus two multi-user schedulers: the Fair Scheduler and the Capacity Scheduler.

Figure 3.6 — FIFO vs Fair vs Capacity scheduling
⚖️ The Fair Scheduler
  • Aims to give every user a fair share of the cluster capacity over time.
  • If a single job is running, it gets all of the cluster.
  • As more jobs are submitted, free task slots are given to jobs so each user gets a fair share.
  • A short job of one user completes in reasonable time even while another user's long job runs — and the long job still makes progress.
  • Jobs are placed in pools; by default each user gets their own pool. A user who submits more jobs than another won't get more cluster resources, on average.
  • Supports preemption: if a pool hasn't received its fair share for a certain time, the scheduler kills tasks in pools running over capacity to give slots to the pool running under capacity.
📦 The Capacity Scheduler
  • A slightly different approach to multi-user scheduling.
  • A cluster is made up of a number of queues (like the Fair Scheduler's pools), which may be hierarchical (a queue may be the child of another queue). Each queue has an allocated capacity.
  • Within each queue, jobs are scheduled using FIFO scheduling (with priorities).
  • In effect, it allows users or organisations (defined using queues) to simulate a separate MapReduce cluster with FIFO scheduling for each.
  • Ideal for shared clusters where resource allocation among queues must follow predefined capacities.
Preemption

A process in resource scheduling where currently allocated resources are forcefully taken away from one task or job and reassigned to another with higher priority. This ensures critical or high-priority jobs get the resources they need, even if it means interrupting or delaying other tasks.

3.8Shuffle and sort@@s3-8@@

Definition

MapReduce guarantees that the input to every reducer is sorted by key. The process by which the system performs the sort — and transfers the map outputs to the reducers as inputs — is known as the shuffle.

  • The shuffle is an area of the codebase where refinements and improvements are continually being made.
  • The shuffle is the heart of MapReduce and is where "the magic" happens.
Figure 3.7 — Shuffle and sort in MapReduce (Textbook Fig. 6-6)

The map side

When the map function starts producing output, it is not simply written to disk. It uses buffering writes in memory and does some presorting for efficiency:

  • 1Each map task has a circular memory buffer that it writes its output to. The buffer is 100 MB by default.
  • 2When the buffer reaches a threshold (io.sort.spill.percent, default 0.80 = 80%), a background thread starts to spill the contents to disk. Map outputs continue to be written to the buffer during the spill, but if the buffer fills up, the map blocks until the spill is complete.
  • 3Spills are written in round-robin fashion to the directories in the mapred.local.dir property, in a job-specific subdirectory.
  • 4Before writing to disk, the thread first divides the data into partitions corresponding to the reducers they'll be sent to.
  • 5Within each partition, the background thread performs an in-memory sort by key, and if there is a combiner function, it is run on the output of the sort. Running the combiner gives a more compact map output → less data to write to local disk and to transfer to the reducer.
  • 6Each time the buffer reaches the spill threshold, a new spill file is created — so there could be several spill files. Before the task finishes, the spill files are merged into a single partitioned and sorted output file.
  • 7It's often a good idea to compress the map output as it's written — faster to write, saves disk space, less data to transfer.
  • 8The output file's partitions are made available to reducers over HTTP. The max number of worker threads serving them is set by tasktracker.http.threads — per TaskTracker, not per map slot.
🧠 Memory trick — map side
"B S P S C M" → Buffer (100 MB) → Spill at 80% → Partition → Sort → Combine → Merge — "Big Spills Please Sweep, Clean, Mop".

The reduce side

  • 1The map output file sits on the local disk of the machine that ran the map task (map outputs always go to local disk; reduce outputs may not). The reduce task needs the map output for its particular partition from several map tasks across the cluster.
  • 2Copy phase: map tasks finish at different times, so the reduce task starts copying their outputs as soon as each completes. It uses a small number of copier threads to fetch in parallel — default five threads (mapred.reduce.parallel.copies).
  • 3Map outputs are copied into the reduce task JVM's memory if small enough; otherwise to disk. When the in-memory buffer reaches a threshold size or number of map outputs, it is merged and spilled to disk (the combiner runs during this merge if specified). As copies accumulate on disk, a background thread merges them into larger, sorted files. Compressed map outputs must be decompressed in memory to merge them.
  • 4Sort phase (really a merge phase — sorting was done on the map side): when all map outputs have been copied, the reduce task merges them maintaining their sort order. This is done in rounds (e.g., 50 map outputs with merge factor 10 → 5 rounds → 5 intermediate files).
  • 5Instead of a final round merging those files into one sorted file, the merge saves a trip to disk by directly feeding the reduce function in the last phase.
  • 6Reduce phase: the reduce function is invoked for each key in the sorted output. The output is written directly to the output file system — typically HDFS.
🧠 Memory trick — reduce side
"Copy → Merge (sort) → Reduce" = "C M R" — "Collect, Mix, Result". The reducer's "sort" phase is actually a merge.
