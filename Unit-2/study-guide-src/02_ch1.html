1.1Data!@@s1-1@@

🗣 In simple words
We live in the data age. Every click, photo, message and sensor reading creates data. There is so much of it that one computer can no longer store or analyse it — that's the problem Hadoop solves.

How big is Big Data?

  • In 2006 the "digital universe" was about 0.18 zettabytes.
  • By 2011 it was forecast to be 1.8 zettabytes — a 10× growth.
  • 1 zettabyte = 1021 bytes = 1,000 exabytes = 1 million petabytes = 1 billion terabytes.
  • To imagine it: like every person on Earth carrying a disk drive.

Real-world examples (from your slides / textbook)

OrganisationHow much data
New York Stock Exchange≈ 1 terabyte of new trade data per day
Facebook≈ 10 billion photos → about 1 petabyte of storage
Ancestry.com (genealogy site)≈ 2.5 petabytes of data
Internet Archive≈ 2 petabytes, growing by 20 terabytes per month
Large Hadron Collider (Geneva)≈ 15 petabytes of data per year
🤖 Machines may generate even more data

Many small streams become Big Data: machine logsRFIDsensorsGPSretail transactionsemail + more. Machine data can be larger than people's data.

📷 MyLifeBits — archiving a whole life

A Microsoft research project: store a photo every minute, all phone calls, emails and documents of one person → about 1 GB of data per month. Add continuous audio/video and it becomes much larger.

😀 The good news

Big Data is here. More data → more opportunities to discover patterns and value. ("More data usually beats better algorithms.")

😟 The bad news

How do we store and analyse it? One machine eventually becomes too small or too slow.

🔑 Bridge to Hadoop
The answer is to distribute storage + distribute processing across many machines. That is exactly what Hadoop does.

1.2Data storage and analysis@@s1-2@@

🗣 In simple words
Hard disks got much bigger over the years, but they did not get much faster at reading data. So reading a full modern disk takes hours. The challenge is not only storing more — it is reading and processing more.
Figure 1.1 — Disk capacity grew much faster than disk speed: bigger capacity ≠ proportionally faster access

The obvious idea: read from many disks at once

1 TBtotal data
→
÷ 100drives
→
10 GBper drive

If 100 drives each hold 1/100th of the data and work in parallel, we can read the whole 1 TB in under 2 minutes instead of 2.5 hours.

Parallelism

Divide a large job into smaller pieces and do them simultaneously.

Figure 1.2 — Parallel reading changes the waiting time
💡 "But aren't 100 disks wasteful?"
No — the 100 disks can hold many datasets (Dataset 1, 2, 3, 4, 5…). Many users share the cluster → shorter analysis times and better hardware utilisation.

Parallel disks create two new problems

Problem 1 · Hardware can fail

More machines → more chances that one disk, node or component fails. Need: reliability.

✅ Solution — Replication: keep redundant copies of the data (Copy 1, Copy 2, Copy 3) so another copy can be used if hardware fails. HDFS uses replication.

Problem 2 · Data must be combined

Results from many disks must be mixed and combined correctly. Need: distributed analysis.

✅ Solution — MapReduce: a simpler programming model. Data from all disks → MAP → shuffle (bring keys + values together) → REDUCE → final result. Map + Reduce hide much of the distributed coordination complexity.

1.3What is Hadoop?@@s1-3@@

Definition

Hadoop is an open-source framework that allows us to store and process large data sets in a parallel and distributed manner. In a nutshell: Hadoop = reliable shared storage + reliable distributed analysis.

  • Hadoop is basically written in Java.
  • Created by Doug Cutting and Mike Cafarella.
  • It contains three core components:
    1. HDFS — the primary data storage system used by Hadoop applications → storage layer.
    2. MapReduce — the processing unit of Hadoop → processing layer.
    3. YARN — resource management layer.
  • Plus Hadoop Common — shared utilities/libraries used by the other modules.
Figure 1.3 — Core components of Hadoop
🧠 Memory trick
"Hadoop has a HMY body" → HDFS = the storage (stomach), MapReduce = the processing (brain), YARN = the manager who decides who gets resources.

A brief history of Hadoop

Figure 1.4 — The journey to Hadoop: Nutch search problem → distributed storage → distributed processing → Hadoop
  • By 2005 Nutch was using MapReduce and NDFS. In February 2006 they became a separate project called Hadoop.
  • Why "Hadoop"? The name is not an acronym. Doug Cutting named it after his child's stuffed yellow toy elephant — short, distinctive and easy to remember.
  • 2006 onward — Yahoo! helps Hadoop grow: Yahoo!'s Grid team adopted Hadoop and provided people, clusters and real-world scale: May 2006 → 300 nodes · Oct 2006 → 600 · Jan 2007 → 900 · Apr 2007 → 1,000 · Mar 2009 → 24,000 nodes.

Why should we use Hadoop?

🏆 Popular

Captured ~90% of the Big Data market; code contributed by IBM, Cloudera, Yahoo!.

📈 Scalable

Add more cheap machines to grow storage & processing.

🛡 Fault tolerant

Replication keeps data safe when machines fail.

🧩 Flexible with data

Handles structured, semi-structured & unstructured data.

The Hadoop ecosystem

HDFS and MapReduce — first look

🗄 HDFS — Hadoop Distributed File System
  • Has a master–slave architecture.
  • Data files are divided into multiple blocks.
  • Blocks are stored in a distributed manner on the cluster of slave nodes; the master stores all the metadata.
  • HDFS has two daemons: NameNode (master) and DataNode (slave).

Full details in Chapter 2.

⚙️ MapReduce
  • The data processing layer of Hadoop.
  • A programming model for processing large datasets by doing work in parallel.
  • Processes data in two phases: Map phase and Reduce phase.
  • MAP: read pieces of data, produce key–value pairs → SHUFFLE: bring values with the same key together → REDUCE: combine each group into the final result.
Figure 1.6 — MapReduce counting letters: input → split → map (emit (letter,1)) → shuffle/sort (group by key) → reduce (add up) → output

1.4Data format — the NCDC weather dataset@@s1-4@@

🗣 In simple words
To learn MapReduce, the textbook uses weather data. Thousands of weather stations record readings hour after hour for many years → a huge dataset. The question we'll answer: "What is the highest temperature recorded in each year?"
  • Data comes from the National Climatic Data Center (NCDC).
  • The data is semi-structured and record-oriented — each line is one weather observation. That makes it a good fit for MapReduce.
  • Each record is stored in a line-oriented ASCII format with fixed-width fields (each field is always at the same character position).

One record — fields we care about

Figure 1.7 — A weather record is a long line of fixed-width fields
📌 Why does the record say -0128?
Temperature is stored as degrees Celsius × 10.
-0128 ÷ 10 = -12.8 °C
The program extracts and interprets this fixed-width temperature field. Missing readings are stored as 9999.
📌 How the files are organised
Originally: one directory per year (e.g., raw/1990/) containing a gzipped file for each weather station (010010-99999-1990.gz, …) — tens of thousands of small files.
Station filesfile 1, file 2, file 3, … (many small files)
→
Preprocessconcatenate all station files of a year
→
One file per yeare.g., 1990 → all readings
→
Ready for MapReduce
🔑 Key point
Hadoop works better with a small number of large files than with many small files. Preprocessing changes only the file organisation — not the meaning of the weather records.

1.5Analyzing the data with Hadoop — Map & Reduce@@s1-5@@

Map and Reduce
  • MapReduce works by breaking the processing into two phases: the map phase and the reduce phase.
  • Each phase has key–value pairs as input and output, the types of which may be chosen by the programmer.
  • The programmer also specifies two functions: the map function and the reduce function.
📌 The task
Find the maximum temperature for each year. Example input: 1990 → 25°C, 31°C, 28°C and 1991 → 27°C, 34°C, 30°C. Wanted output: 1990 → 31°C | 1991 → 34°C.
Step 1 · MAP — extract only what we need The mapper reads each long weather record (station + date + time + wind + visibility + temperature + pressure + …) and emits just (year, temperature). It also filters out bad or missing records.
(1990, 25) (1990, 31) (1990, 28) (1991, 27) …  →  Key = Year | Value = Temperature
Input to map: key = line offset in the file (ignored), value = the line of text (the record).
Step 2 · SHUFFLE & SORT — group the same years (done automatically by Hadoop) Before reduce, the framework sorts and groups values having the same key:
1990 → [25, 31, 28]   1991 → [27, 34, 30]   (textbook: 1949 → [111, 78], 1950 → [0, 22, −11])
Step 3 · REDUCE — find the maximum in each group The reduce function receives (key, list of values) and iterates through the list picking the maximum:
MAX(111, 78) = 111   MAX(0, 22, −11) = 22 → final output (1949, 111), (1950, 22).
Figure 1.8 — MapReduce logical data flow for the maximum-temperature example (Textbook Fig. 2-1)
🔑 Who does what?
The programmer writes only two things: the map function ("for every weather record, extract the year and temperature") and the reduce function ("for every year, find the maximum temperature"). Hadoop takes care of distributing the work, grouping the intermediate key–value pairs, and passing them to reducers.
🧠 Memory trick
MAP = Extract · SHUFFLE = Group · REDUCE = Summarise — "E G S: Every Group Summarised".

1.6Java MapReduce — Mapper, Reducer, Driver@@s1-6@@

To run a MapReduce program, we need three things:

1 · Map function (Mapper class)

Reads each input record (one line of weather data), extracts year & temperature, filters out bad/missing records, outputs intermediate key–value pairs <Year, Temperature>.

2 · Reduce function (Reducer class)

Receives a key and a list of all values (a year and all its temperatures), finds the maximum, outputs <Year, Max Temperature>.

3 · Code to run the job (Driver / Main class)

Configures the job (name, input & output paths), specifies the Mapper and Reducer classes, sets the key and value types, submits the job to Hadoop and waits for it to finish.

In short: a MapReduce program has a Mapper, a Reducer, and a Driver to run the job.

The Mapper

public class MaxTemperatureMapper
    extends Mapper<LongWritable, Text, Text, IntWritable> {
  private static final int MISSING = 9999;
  @Override
  public void map(LongWritable key, Text value, Context context)
      throws IOException, InterruptedException {
    String line = value.toString();
    String year = line.substring(15, 19);            // year is at characters 15–19
    int airTemperature;
    if (line.charAt(87) == '+') {                    // parseInt doesn't like leading plus signs
      airTemperature = Integer.parseInt(line.substring(88, 92));
    } else {
      airTemperature = Integer.parseInt(line.substring(87, 92));
    }
    String quality = line.substring(92, 93);
    if (airTemperature != MISSING && quality.matches("[01459]")) {  // skip bad/missing readings
      context.write(new Text(year), new IntWritable(airTemperature));
    }
  }
}

The Reducer

Reducer<Text, IntWritable, Text, IntWritable> = <Year, Temperatures, Year, Maximum Temperature>. The reducer's input types must match the mapper's output types.

public class MaxTemperatureReducer
    extends Reducer<Text, IntWritable, Text, IntWritable> {
  @Override
  public void reduce(Text key, Iterable<IntWritable> values, Context context)
      throws IOException, InterruptedException {
    int maxValue = Integer.MIN_VALUE;
    for (IntWritable value : values) {
      maxValue = Math.max(maxValue, value.get());      // keep the largest
    }
    context.write(key, new IntWritable(maxValue));
  }
}

The Driver (application that runs the job)

public class MaxTemperature {
  public static void main(String[] args) throws Exception {
    if (args.length != 2) {
      System.err.println("Usage: MaxTemperature <input path> <output path>");
      System.exit(-1);
    }
    Job job = new Job();
    job.setJarByClass(MaxTemperature.class);           // Hadoop finds the JAR to ship to the cluster
    job.setJobName("Max temperature");
    FileInputFormat.addInputPath(job, new Path(args[0]));   // input path
    FileOutputFormat.setOutputPath(job, new Path(args[1])); // output dir (must NOT exist)
    job.setMapperClass(MaxTemperatureMapper.class);
    job.setReducerClass(MaxTemperatureReducer.class);
    job.setOutputKeyClass(Text.class);
    job.setOutputValueClass(IntWritable.class);
    System.exit(job.waitForCompletion(true) ? 0 : 1);   // submit and wait
  }
}
💡 Hadoop data types
Hadoop uses its own types optimised for network serialisation: LongWritable ≈ Java long, Text ≈ Java String, IntWritable ≈ Java int.

A test run

After writing the Mapper, Reducer and Driver, don't immediately run them on years of data. First run on a very small sample containing only 5 weather records:

% export HADOOP_CLASSPATH=hadoop-examples.jar
% hadoop MaxTemperature input/ncdc/sample.txt output

Hadoop prints a log: Running job: job_local_0001 … map 100% reduce 100% … Job completed successfully, followed by counters, e.g.:

  • Map input records = 5, Map output records = 5
  • Reduce input groups = 2 (two years), Reduce input records = 5
  • Reduce output records = 2
% cat output/part-r-00000
1949    111
1950    22

The output file is named part-r-00000 (r = reducer output, 00000 = reducer number). 111 = 11.1°C and 22 = 2.2°C.

1.7Scaling out & data flow@@s1-7@@

🗣 In simple words
On real (big) data, Hadoop cuts the input into pieces called splits, runs one map task per split on many machines at the same time — preferably on the machine that already holds that piece of data — and then sends the map results to the reducers.
MapReduce job

A unit of work that the client wants to be performed. It consists of the input data, the MapReduce program, and configuration information.

  • Hadoop runs the job by dividing it into tasks of two types: map tasks and reduce tasks.
  • Tasks are scheduled using YARN and run on nodes in the cluster. If a task fails, it is automatically rescheduled on a different node.
  • Hadoop divides the input into fixed-size pieces called input splits (or just splits). It creates one map task for each split, which runs the map function for each record in the split.
  • Why many small splits? The time to process each split is small compared to the whole input → work is better load-balanced: a faster machine can process proportionally more splits than a slower one.

Data locality optimisation

Hadoop does its best to run the map task on a node where the input data resides in HDFS, because it doesn't use valuable cluster bandwidth. This is called the data locality optimisation.

Figure 1.9 — (a) data-local, (b) rack-local and (c) off-rack map tasks (Textbook Fig. 2-2)
CaseWhen it happensCost
(a) Data-localMap task runs on the same node that stores the block — the preferred case.✅ No network transfer
(b) Rack-localAll nodes holding the block's replicas are busy → scheduler finds a free map slot on a node in the same rack.⚠️ Transfer within the rack
(c) Off-rackVery occasionally even that is impossible → a node in a different rack is used.❌ Inter-rack network transfer
🔑 Why is the optimal split size = HDFS block size (128 MB)?
Because a block is the largest size of input that can be guaranteed to be stored on a single node. If a split spanned two blocks, it's unlikely any one node stores both, so part of the split would have to travel over the network — less efficient than running the whole map task on local data.
🧠 Memory trick
"Home → Neighbour → Other town": data-local (your own house), rack-local (your neighbour on the same street), off-rack (another town — slowest trip).

Data flow with a single reduce task

  • Map tasks write their output to the local disk, not to HDFS — map output is intermediate: it's processed by reducers and thrown away once the job is complete.
  • The reduce task's input is the sorted map outputs from all mappers, transferred over the network (copy), merged, then passed to the reduce function.
  • Reduce output is stored in HDFS for reliability (first replica on the local node, other replicas off-rack).
Figure 1.10 — MapReduce data flow with a single reduce task (Textbook Fig. 2-3). Dotted boxes = nodes; dotted arrows = transfer on a node; solid arrows = transfer between nodes.

Data flow with multiple reduce tasks

  • The number of reduce tasks is not governed by the size of the input — it is specified independently.
  • With multiple reducers, map tasks partition their output, creating one partition for each reduce task.
  • There can be many keys in each partition, but all records for a given key are in a single partition.
  • Partitioning can be controlled by a user-defined partitioning function, but normally the default partitioner — which buckets keys using a hash function — works very well.
  • Because each reduce task is fed by many map tasks, this data flow is colloquially known as "the shuffle".
Figure 1.11 — MapReduce data flow with multiple reduce tasks (Textbook Fig. 2-4)
💡 Extra (textbook): zero reducers & combiners
A job can have zero reduce tasks when no shuffle is needed — then map tasks write output straight to HDFS. A combiner is an optional "mini-reducer" run on map output to cut the data sent over the network (e.g., max of a map's own values first). Your slide's driver uses job.setCombinerClass(MaxTemperatureReducer.class) for this.
