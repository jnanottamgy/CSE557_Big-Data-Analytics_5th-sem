CHAPTER 1 · Basics of Hadoop

  • Data! 2006: 0.18 ZB → 2011: 1.8 ZB (10×). 1 ZB = 1021 B = 1 billion TB. NYSE 1 TB/day · Facebook 10 bn photos ≈ 1 PB · Ancestry 2.5 PB · Internet Archive 2 PB (+20 TB/month) · LHC 15 PB/yr. MyLifeBits ≈ 1 GB/month.
  • Storage problem: 1990 disk 1,370 MB @ 4.4 MB/s (5 min); now 1 TB @ 100 MB/s (> 2.5 hr). Read 1 TB from 100 disks in parallel → < 2 min.
  • 2 problems: hardware failure → replication (HDFS); combining data → MapReduce.
  • Hadoop = open-source framework to store & process large data in a parallel, distributed manner; Java; Doug Cutting & Mike Cafarella; = reliable shared storage + reliable distributed analysis.
  • Components: HDFS (storage), MapReduce (processing), YARN (resource mgmt), Common.
  • History: Nutch 2002 → GFS paper 2003 → NDFS 2004 → MapReduce paper 2004 → Nutch+MR 2005 → Hadoop Feb 2006. Named after a toy elephant (not an acronym). Yahoo!: 24,000 nodes by 2009; Apache top-level Jan 2008; 1 TB sort in 209 s on 900 nodes.
  • Why Hadoop: ~90% of market, scalable, fault tolerant, flexible.
  • NCDC data: semi-structured, record-oriented, fixed-width ASCII; temp = °C × 10 (-0128 = -12.8 °C); 9999 = missing; preprocess many small station files → one file per year.
  • MapReduce: 2 phases (map, reduce), key–value in & out; programmer writes map & reduce functions. Map = extract (year, temp) · Shuffle = group by key · Reduce = max. Output: (1949, 111), (1950, 22).
  • Java: Mapper<LongWritable, Text, Text, IntWritable>; Reducer<Text, IntWritable, Text, IntWritable>; Driver sets paths, classes, types, waitForCompletion. Output file part-r-00000.
  • Scaling out: job = input + program + config; tasks = map + reduce; scheduled by YARN; input splits (one map per split); data-local → rack-local → off-rack; split size = block size (128 MB).
  • Data flow: map output → local disk; reducers copy & merge; reduce output → HDFS. Multiple reducers → partition (hash partitioner) → "the shuffle".

CHAPTER 2 · HDFS

  • DFS = file system managing storage across a network of machines; main challenge: tolerate node failure without data loss.
  • HDFS design: very large files, streaming access (write once, read many), commodity hardware. Not for: low latency (use HBase), lots of small files (NameNode memory), multiple writers/arbitrary modifications.
  • Blocks: 128 MB default (disk block 512 B; FS block few KB). A 1 MB file uses 1 MB. Benefits: file > any disk; simpler storage; fits replication (3 copies).
  • NameNode (master): namespace, file tree, metadata; persisted as namespace image + edit log. DataNodes (workers): store/retrieve blocks, send block reports.
  • Resilience: write metadata to multiple FS (local + NFS, synchronous & atomic); Secondary NameNode merges image + edit log (not a backup).
  • Federation (2.x): many NameNodes, each manages part of namespace (/user, /share); namespace volume = metadata + block pool; independent.
  • HA: NameNode = SPOF; cold restart = load image + replay edit log + block reports → 30+ min. Fix: active–standby pair; shared edit log; block reports to both; client failover; standby does checkpoints.
  • File read (6): open() on DistributedFileSystem → RPC NameNode for block locations (sorted by proximity) → read() on FSDataInputStream/DFSInputStream → stream from closest DataNode → next block → close(). Failures: next closest DN; checksum → other replica + report.
  • File write (7): create() → RPC NameNode create (checks exists/permissions, else IOException) → write: packets → data queue → DataStreamer → pipeline of 3 DNs → ack queue → close() flushes → complete. Failure: close pipeline, re-queue acks, new block ID, rebuild pipeline.

CHAPTER 3 · Developing MapReduce apps

  • Workflows: more jobs, not more complex jobs; or use Pig, Hive, Cascading, Crunch, Spark. Mean-max = Job 1 (station, date → max) + Job 2 (station, day-month → mean). Linear chain via JobClient.runJob(); DAG via JobControl.
  • MRUnit + JUnit: MapDriver (1950, −11), ReduceDriver ([10,5] → 10), local job runner for whole job.
  • Job run: submit() / waitForCompletion(); mapreduce.framework.name = local / classic / yarn.
  • MR1: Client, JobTracker, TaskTrackers, DFS. Submission (1–4: job ID, check output, compute splits, copy JAR high replication, submitJob) · Initialisation (5–6: queue, one map/split, mapred.reduce.tasks) · Assignment (7: heartbeat) · Execution (8–10: localise JAR, TaskRunner launches new JVM).
  • YARN (Yet Another Resource Negotiator, 2010, Yahoo!; MR1 bottleneck ~4,000 nodes): JobTracker split into ResourceManager + ApplicationMaster. Entities: Client, RM, NMs, MRAppMaster, DFS. Steps 1–4 submit · 5a/5b launch AM · 6 init · 7 splits · 8 request containers (maps first; reduces after 5%) · 9a/9b start container · 10 YarnChild localises · 11 run.
  • Failures MR1: task (exception/JVM exit), TaskTracker (no heartbeat; blacklist >4 failed tasks), JobTracker (SPOF → job fails). YARN: task (4 attempts), AM (RM restarts it), NM (10 min timeout; AM blacklists >3 failures), RM (checkpoint recovery).
  • Scheduling: FIFO (default MR1) · Fair (pools per user, fair share over time, preemption) · Capacity (hierarchical queues with capacity, FIFO inside). Preemption = forcefully reassigning resources to higher-priority work.
  • Shuffle & sort: reducer input sorted by key. Map side: 100 MB circular buffer → spill at 80% → partition → in-memory sort → combiner → merge spills → compress → HTTP. Reduce side: copy (5 threads) → merge ("sort") in rounds → reduce → HDFS.
