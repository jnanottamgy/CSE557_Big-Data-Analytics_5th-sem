Ch 1 · Types of Digital Data

Data (U1 §1.1)

Data = quantities, characters or symbols on which operations are performed by a computer; stored & transmitted as electrical signals; recorded on magnetic, optical or mechanical media. Data → Information → Insights. Types: Quantitative (discrete = counted, continuous = measured) vs Qualitative (descriptive). Sources: internal & external (outside the firewall); homogeneous & heterogeneous.

Structured data (U1 §1.3)

  • Stored in RDBMS (relational model). Cardinality = no. of rows; degree = no. of columns.
  • Design: fields + data types → constraints (UNIQUE, NOT NULL, business rule e.g. ≥ 50, permissible values e.g. CS/IS/MS) → relate tables by common column (PRIMARY KEY / FK).
  • Sources: Oracle, DB2, SQL Server, Teradata, MySQL, PostgreSQL, MS Access, Excel, OLTP.
  • Ease of working (ISIST): Insert/update/delete (DML) · Security (encryption, tokenization) · Indexing (faster SELECT) · Scalability (scale up the server) · Transactions (ACID).
  • ACID: Atomicity (all or nothing) · Consistency (valid state → valid state) · Isolation (as if alone) · Durability (permanent).

Semi-structured data (U1 §1.4)

  • 5 features: not a relational data model · tags segregate semantic elements · tags enforce hierarchies · no separation of data & schema · same-class entities may have different attributes / order.
  • 4 characteristics: inconsistent structure · self-describing (label/value pairs) · schema blended with data · attributes not known beforehand.
  • XML ↔ SOAP · JSON ↔ REST · MongoDB & Couchbase/CouchDB store JSON natively.

Unstructured data (U1 §1.5–1.6)

  • No data model; can't be stored in rows/columns; difficult to search; e.g. Aadhaar images, CCTV, social media.
  • Machine-generated: satellite images, atmospheric data, radar, CCTV, medical imaging. Human-generated: emails, office docs, text messages, audio, social media.
  • Terminology issues (3): structure may be implied · structure not helpful for the task · structure unanticipated.
  • 7 techniques: Data mining (= KDD; association rules — bread & butter, regression — marks from study hours, collaborative filtering — recommendations) · Text analytics (categorisation, clustering, sentiment, entity extraction) · NLP (understand human language) · Noisy text analytics ("u coming tmrw??") · Manual tagging with metadata · POS tagging (noun/verb…) · UIMA (open-source, by IBM, content analytics).

Ch 2 · Introduction to Big Data

Characteristics & evolution (U1 §2.1–2.2)

  • 3 Cs: Composition (structure, sources, granularity, types, static/streaming) · Condition (usable as is or needs cleansing?) · Context (where/why generated).
  • Evolution: ≤1970s mainframes — primitive & structured → 1980s–90s RDBMS — complex & relational → 2000s+ WWW & IoT — complex & unstructured (data explosion).

Definition (U1 §2.3)

Gartner

"Big Data is high-volume, high-velocity and high-variety information assets that demand cost-effective, innovative forms of information processing for enhanced insight and decision making."

Data → Information → Actionable intelligence → Better decisions → Enhanced business value. Informal: beyond human/technical infrastructure · today's BIG is tomorrow's NORMAL · TB/PB/ZB · 3 Vs.

Challenges with Big Data (U1 §2.4)

6: huge growth (useful vs noise) · cloud & virtualisation · data retention (how long) · lack of skilled people · capture/storage/processing/security · visualisation (+ shortage of experts). Figure: capture, storage, curation, search, analysis, transfer, visualisation, privacy.

3 Vs + others (U1 §2.5–2.6)

  • Volume — KB→MB→GB→TB→PB→EB→ZB→YB (×1024). Sources: internal (file systems, SQL, NoSQL, archives) · external (public web: Wikipedia, weather, census) · both (sensors, machine logs, social media, business apps, media, docs).
  • Velocity — batch → periodic → near real time → real time.
  • Variety — structured + semi-structured + unstructured.
  • Not definitional: Veracity (trustworthiness: noise, bias) & Validity (accuracy for the problem) · Volatility (how long data stays valid) · Variability (inconsistent flow, sudden peaks).

Ch 3 · Big Data Analytics

What BDA is (U1 §3.1–3.2)

  • Examples: Amazon recommendations; 500-truck urgent delivery. Large data → analyse → patterns → better decisions.
  • Pyramid: Data (collect) → Information (organise) → Knowledge (summarise, analyse) → Actionable insights (synthesise) → Decision.
  • Data from: websites, billing (POS), ERP, CRM, RFID, social media.
  • Is (6): technology-enabled · deeper insights · competitive edge · handshake of IT + data scientists + business users · large & varied data · moving code to data.
  • Isn't (6): only volume · just technology · replacement for RDBMS · replacement for data warehouse · only for Google/Amazon · one-size-fits-all RDBMS.
  • Hype (3): data growth · cheaper storage · tools available.

Top challenges · importance (U1 §3.4–3.5)

  • 7 top challenges: Scale · Security · Schema (dynamic) · Continuous availability (24/7) · Consistency · Partition tolerance · Data quality.
  • 4 approaches: Reactive–BI · Reactive–BDA (huge but static) · Proactive–analytics (traditional DB limits) · Proactive–BDA ★ (TB/PB/EB, high-performance).

Data science & data scientist (U1 §3.6–3.7)

  • Data science = science of extracting knowledge from data (maths, statistics, IT, ML, pattern recognition). Uses: weather, oil drilling, seismic, fraud, social media, retail.
  • Skills (BTM): Business acumen (domain, strategy, problem solving, communication, presentation, inquisitiveness) · Technology (RDBMS, NoSQL, programming, DW, data mining, visualisation) · Mathematics (maths, statistics, algorithms, ML, pattern recognition, NLP).
  • Process: collect → prepare → analyse → visualise → communicate → decide.
  • 4 responsibilities: data management · analytical techniques · business/domain expertise · communication & presentation.

Terminologies (U1 §3.8–3.9)

  • In-memory analytics: keep relevant data in RAM → faster, rapid deployment, better insights, minimal IT.
  • In-database processing: OLTP → ETL → EDW; run computations inside the DB → no export.
  • SMP: shared main memory, one OS, tightly coupled, caches + system bus. MPP: each processor own memory + OS, messaging, harder to program.
  • Parallel: tightly coupled, user unaware. Distributed: loosely coupled machines, own users, data spread.
  • Shared memory / shared disk / shared nothing. SN advantages: fault isolation + scalability.
  • CAP (Brewer): Consistency (read = last write) · Availability (always a response) · Partition tolerance (works despite network break) → pick 2. CA: RDBMS (MySQL, PostgreSQL) · CP: HBase, MongoDB, Redis, MemcacheDB, BigTable · AP: Riak, Cassandra, CouchDB, Dynamo. Prefer C for bank balance; A for feeds/caches.
