Ch 1 · Basics of Hadoop

Data! · storage & analysis (U2 §1.1–1.2)

  • NYSE 1 TB/day · Facebook 10 bn photos ≈ 1 PB · Ancestry 2.5 PB · Internet Archive 2 PB (+20 TB/month) · LHC 15 PB/yr · MyLifeBits ≈ 1 GB/month. Machines (logs, RFID, sensors, GPS) generate even more.
  • Problem: disk capacity grew much faster than transfer speed → read from 100 disks in parallel.
  • New problems: hardware failure → solved by replication (HDFS) · combining data → solved by MapReduce.

Hadoop (U2 §1.3)

Definition

Open-source framework to store and process large data sets in a parallel and distributed manner. Hadoop = reliable shared storage + reliable distributed analysis.

  • Written in Java; by Doug Cutting & Mike Cafarella; named after a toy elephant (not an acronym).
  • Components: HDFS (storage) · MapReduce (processing) · YARN (resource management) · Common (utilities).
  • History: Nutch 2002 → Google GFS 2003 → NDFS 2004 → MapReduce paper 2004 → Nutch + MR 2005 → Hadoop Feb 2006. Yahoo! scaled it (24,000 nodes by 2009).
  • Why: ~90% market, scalable, fault tolerant, flexible with data.
  • Ecosystem: Hive, Pig, Mahout, Spark (SQL, Streaming, MLlib, GraphX), HBase, Cassandra, ZooKeeper, Flume, Kafka, Sqoop, Storm.

NCDC weather data (U2 §1.4)

Semi-structured, record-oriented, fixed-width ASCII line per observation: station ID, date, time, … air temperature (°C × 10), pressure. 9999 = missing. Many small gzipped station files → preprocess into one file per year.

Map & Reduce (U2 §1.5–1.6)

  • Two phases, each with key–value input/output; programmer writes map and reduce functions.
  • Map = extract (year, temp), filter bad records · Shuffle & sort = group by key: 1949 → [111, 78] · Reduce = max → (1949, 111), (1950, 22).
  • Mapper<LongWritable, Text, Text, IntWritable> = (offset, line) → (year, temp). Reducer<Text, IntWritable, Text, IntWritable>.
  • Driver: Job, setJarByClass, input/output paths (output dir must not exist), setMapperClass, setReducerClass, output key/value classes, waitForCompletion. Output: part-r-00000.
  • Test run on 5 records: hadoop MaxTemperature input/ncdc/sample.txt output.

Scaling out & data flow (U2 §1.7)

  • Job = input + program + config. Tasks = map + reduce, scheduled by YARN; failed tasks rescheduled.
  • Input split → one map task per split; small splits = better load balancing.
  • Data locality: data-local → rack-local → off-rack. Optimal split = block size (largest input guaranteed on one node).
  • Map output → local disk (intermediate); reduce output → HDFS.
  • Multiple reducers: map output partitioned (one partition per reducer, default hash partitioner) → "the shuffle". Zero reducers possible. Combiner = mini-reducer on map output.
Ch 2 · HDFS

Design (U2 §2.1–2.2)

Definition

HDFS is a file system designed for storing very large files with streaming data access patterns, running on clusters of commodity hardware.

  • Good at (LSC): very large files (MB→PB) · streaming = write once, read many · cheap commodity hardware (keeps working when nodes fail).
  • Bad at (LSM): low-latency access (use HBase) · lots of small files (NameNode memory: millions OK, billions not) · multiple writers / arbitrary modifications (single writer, append at end).

Blocks (U2 §2.3)

128 MB default; a 1 MB file uses 1 MB. Benefits: file can be larger than any disk · simpler storage subsystem · fits replication (3 copies on separate machines).

NameNode & DataNodes (U2 §2.4)

  • Master–worker. NameNode: namespace, file tree, metadata — persisted as namespace image + edit log; block locations rebuilt from DataNode reports. DataNodes: store/retrieve blocks, send block reports.
  • Lose the NameNode = lose the file system. Protect it by: (1) writing metadata to multiple file systems (local + NFS, synchronous & atomic); (2) Secondary NameNode — periodically merges image + edit log (checkpoint); not a backup.

Federation & HA (U2 §2.5–2.6)

  • Federation (2.x): NameNode memory limits scaling → add NameNodes, each owns part of the namespace (/user, /share). Namespace volume = metadata + block pool; independent; one failing doesn't affect others.
  • HA: NameNode = SPOF. Cold start needs (i) load image (ii) replay edit log (iii) block reports → leave safe mode = 30+ min. Fix: active–standby pair: shared edit log (HA storage) · DataNodes report to both · client failover · standby does checkpoints.

File read — 6 steps (U2 §2.7)

  1. open() on DistributedFileSystem.
  2. RPC to NameNode → block locations, DataNodes sorted by proximity; returns FSDataInputStream (wraps DFSInputStream).
  3. read() → connect to closest DataNode for block 1.
  4. Data streamed to client.
  5. End of block → close, find best DataNode for next block (asks NN for next batch).
  6. close().

Failure: try next closest DN, remember bad DNs · checksum fails → read another replica + report corrupt block to NN.

File write — 7 steps (U2 §2.8)

  1. create() on DistributedFileSystem.
  2. RPC to NN to create file (no blocks); checks exists? permission? else IOException; returns FSDataOutputStream.
  3. write() → packets → data queue → DataStreamer asks NN for blocks → pipeline of 3 DNs.
  4. Write packet: DN1 stores & forwards → DN2 → DN3.
  5. Ack packet back; removed from ack queue when all DNs ack.
  6. close() flushes remaining packets, waits for acks.
  7. Tell NN file complete.

Failure: close pipeline · ack-queue packets to front of data queue · good block gets new identity (partial one deleted later) · remove failed DN, new pipeline from 2 good DNs.

Ch 3 · Developing a MapReduce Application

Workflows · MRUnit · job run (U2 §3.1–3.3)

  • Complex problem → more jobs, not more complex jobs (or Pig, Hive, Cascading, Crunch, Spark). Mean-max = Job 1 (station, date → max) + Job 2 (station, day-month → mean).
  • Linear chain: JobClient.runJob() one after another; DAG → JobControl (stores jobs, dependencies, order, monitors, skips dependents on failure).
  • MRUnit + JUnit: MapDriver (record → (1950, −11)), ReduceDriver ([10, 5] → 10), whole job via local job runner.
  • submit() / waitForCompletion(); mapreduce.framework.name = local (one JVM) / classic (MR1) / yarn (MR2).

Classic MapReduce (MR1) — 10 steps (U2 §3.4)

Entities: Client · JobTracker (coordinates) · TaskTrackers (run tasks) · DFS.

  • Submission 1–4: JobSubmitter · new job ID from JobTracker · check output dir · compute splits · copy JAR (high replication), config, splits to shared FS · submitJob().
  • Initialisation 5–6: internal queue → scheduler creates job object · retrieve splits · one map task per split, reducers = mapred.reduce.tasks.
  • Assignment 7: TaskTracker heartbeat → gets a task.
  • Execution 8–10: localise JAR + distributed cache · TaskRunner launches new JVM · run task (user bugs can't crash TaskTracker).

YARN (MR2) — 11 steps (U2 §3.5)

Why: MR1 bottleneck at ~4,000 nodes; JobTracker did scheduling + monitoring → split into ResourceManager + per-app ApplicationMaster. YARN = Yet Another Resource Negotiator (Yahoo!, 2010). Entities: Client · ResourceManager · NodeManagers · MRAppMaster · DFS.

  • Submission 1–4: application ID from RM · checks · copy resources · submitApplication().
  • Init 5a/5b–7: scheduler allocates container, RM launches MRAppMaster · AM initialises job · retrieves splits.
  • Assignment 8: AM requests containers — maps first (higher priority); reduces after 5% maps done (uber task = tiny job in AM's JVM).
  • Execution 9a/9b–11: AM asks NodeManager to start container · YarnChild localises resources · runs task. Tasks report progress to the AM.

Scheduling (U2 §3.7)

  • FIFO (MR1 default). Fair: every user a fair share over time; pools (one per user); single job gets whole cluster; short jobs finish; preemption. Capacity: hierarchical queues with fixed capacity; FIFO within queue; like a separate cluster per org.
  • Preemption = forcefully take resources from one job and give to a higher-priority one.

Shuffle & sort (U2 §3.8)

  • Guarantee: reducer input sorted by key; sort + transfer of map output = shuffle ("heart of MapReduce").
  • Map side: 100 MB circular buffer → spill at 80% (round-robin to mapred.local.dir) → partition → in-memory sort → combiner → merge spills into one sorted, partitioned file → (compress) → served over HTTP.
  • Reduce side: copy phase (5 threads, starts as each map finishes) → merge ("sort") phase in rounds → reduce phase per key → output to HDFS.
