Unit 2

Data Analytics with Hadoop

The story of this unit One disk is too slow to read Big Data, so we read from many disks in parallel. That creates two problems — machines fail and results must be combined. Hadoop solves the first with HDFS (blocks stored 3 times) and the second with MapReduce (map → shuffle → reduce). We then see exactly how files are read and written, how a job runs (classic MapReduce, then YARN), how it survives failures, how jobs are scheduled, and the shuffle at its heart.
Textbook: Tom White, Hadoop: The Definitive Guide

2.1Why Hadoop? What is Hadoop?@@b1@@

Data! The digital universe grew from 0.18 ZB (2006) to 1.8 ZB (2011) — 1 ZB = 1021 bytes = 1 billion TB. NYSE creates ~1 TB a day, Facebook stores ~10 billion photos (≈ 1 PB), the Large Hadron Collider ~15 PB a year. Machines (logs, RFID, sensors, GPS) generate even more. Good news: more data = more value. Bad news: how do we store and analyse it?

🗣 In plain words
Disks got huge but not much faster to read. So the fix is to read from many disks at the same time.
{{fig:u2_disk|Capacity grew ~730×, speed only ~23×}} {{fig:u2_par|1 TB split across 100 disks is read in under 2 minutes}}

Reading 100 disks in parallel creates two new problems:

1 · Hardware fails

More machines = more failures. Solution: replication — keep redundant copies. HDFS does this.

2 · Data must be combined

Results from many disks must be merged correctly. Solution: MapReduce — map → shuffle → reduce, hiding the coordination.

Definition — Hadoop

An open-source framework that allows us to store and process large data sets in a parallel and distributed manner. In a nutshell: reliable shared storage + reliable distributed analysis.

  • Written in Java; created by Doug Cutting and Mike Cafarella; named after Doug's child's toy elephant (not an acronym).
  • Core components: HDFS — storage layer · MapReduce — processing layer · YARN — resource management layer · Common — shared utilities.
  • Why use it: ~90% of the Big Data market · scalable · fault tolerant · flexible with any data.
  • History: Nutch search engine (2002) → Google's GFS paper (2003) → NDFS (2004) → Google's MapReduce paper (2004) → Nutch on MapReduce (2005) → Hadoop, Feb 2006. Yahoo! grew it to 24,000 nodes (2009); Apache top-level project (Jan 2008); sorted 1 TB in 209 s on 900 nodes (2008).

2.2MapReduce with the weather example@@b2@@

🗣 In plain words
Map = each worker reads its piece and writes down only what matters as (key, value) pairs. Shuffle & sort = Hadoop collects all values with the same key together. Reduce = combine each group into one answer.
{{fig:u2_letters|MapReduce counting letters — input → split → map → shuffle → reduce → output}}

The dataset: NCDC weather data — semi-structured and record-oriented. Each line is one observation with fixed-width fields. Temperature is stored as °C × 10 (so −0128 = −12.8 °C); 9999 means missing. The original tens of thousands of small station files are preprocessed into one file per year, because Hadoop prefers a few large files.

{{fig:u2_record|One weather record}}
Map and Reduce

MapReduce breaks processing into two phases — map and reduce. Each phase has key–value pairs as input and output. The programmer writes two functions: the map function and the reduce function.

Task: find the maximum temperature for each year.

  1. Map — input is (line offset, line). The mapper extracts (year, temperature) and drops bad/missing records: (1950, 0), (1950, 22), (1950, −11), (1949, 111), (1949, 78).
  2. Shuffle & sort (automatic) — group by key: 1949 → [111, 78], 1950 → [0, 22, −11].
  3. Reduce — pick the max of each list: (1949, 111), (1950, 22).
{{fig:u2_flow|✏️ must-draw · MapReduce logical data flow for maximum temperature}}

The three Java pieces:

  • Mapper — Mapper<LongWritable, Text, Text, IntWritable> = (offset, line) → (year, temp). Reads year at chars 15–19 and temperature at 87–92, skips 9999 and bad quality codes, then context.write(year, temp).
  • Reducer — Reducer<Text, IntWritable, Text, IntWritable>: loops through the values keeping Math.max; input types must match the mapper's output types.
  • Driver — creates a Job, sets the JAR, input path, output path (must not exist), mapper and reducer classes, output key/value types, then waitForCompletion(true).
public void reduce(Text key,
    Iterable<IntWritable> values, Context ctx) {
  int max = Integer.MIN_VALUE;
  for (IntWritable v : values)
    max = Math.max(max, v.get());
  ctx.write(key, new IntWritable(max));
}

% hadoop MaxTemperature input/ncdc/sample.txt output
% cat output/part-r-00000
1949    111
1950    22

Hadoop types: LongWritable ≈ long, Text ≈ String, IntWritable ≈ int. Test first on a 5-record sample.

🧠 Memory trick
Map = Extract · Shuffle = Group · Reduce = Summarise — "Every Group Summarised". The programmer writes only map + reduce; Hadoop does distribution, grouping and passing to reducers.

2.3Scaling out: splits, data locality and data flow@@b3@@

  • A MapReduce job = input data + MapReduce program + configuration. Hadoop splits it into map tasks and reduce tasks, scheduled by YARN; a failed task is re-run on another node.
  • The input is cut into fixed-size input splits; one map task per split. Many small splits = better load balancing (fast machines just do more splits).
  • Data locality optimisation: run the map task on the node that already holds that block, so no network bandwidth is used.
{{fig:u2_local|Data-local (a), rack-local (b) and off-rack (c) map tasks}}

Order of preference: data-local (same node) → rack-local (same rack, if the data's nodes are busy) → off-rack (other rack, inter-rack transfer). Optimal split size = block size (128 MB), because a block is the largest input guaranteed to be on one node; a split spanning two blocks would need network transfer.

  • Map output goes to local disk (it is temporary); reducers copy it over the network, merge it, reduce, and write the result to HDFS (replicated).
  • With multiple reducers, each map partitions its output — one partition per reducer, all values of a key in the same partition, using the default hash partitioner. Because every reducer is fed by many mappers, this is called "the shuffle".
  • Number of reducers is chosen independently (can even be zero). A combiner is a mini-reducer run on map output to cut network traffic.
{{fig:u2_single|Data flow with a single reduce task}} {{fig:u2_multi|✏️ must-draw · Data flow with multiple reduce tasks}}
🧠 Memory trick
Locality = "Home → Neighbour → Other town".

2.4HDFS: design, blocks, NameNode and DataNodes@@b4@@

When a dataset outgrows one machine, it is partitioned across many. File systems that manage storage across a network of machines are distributed file systems. They are harder than normal file systems because of networking — the biggest challenge is surviving node failure without losing data. Hadoop's is HDFS (it can also use the local file system or Amazon S3).

Definition — design of HDFS (word-for-word)

HDFS is a file system designed for storing very large files with streaming data access patterns, running on clusters of commodity hardware.

HDFS is good atHDFS is bad at
Very large files — hundreds of MB to TB; clusters hold PB.
Streaming access — write once, read many times; reading the whole dataset fast matters more than the first record.
Commodity hardware — cheap machines; keeps working through failures.		Low-latency access (tens of ms) — it's built for throughput; use HBase.
Lots of small files — the NameNode keeps metadata in memory: millions OK, billions not.
Multiple writers / random edits — one writer, writes only at the end of the file.
🧠 Memory trick
Good: "L S C" (Large, Streaming, Cheap). Bad: "L S M" (Low latency, Small files, Multiple writers).

Blocks

A disk block is 512 bytes, a normal file-system block a few KB, but an HDFS block is 128 MB by default. Files are cut into block-sized chunks stored independently. A file smaller than a block does not take a full block (a 1 MB file uses 1 MB).

{{fig:u2_blocks|A 500 MB file → 4 blocks, each stored 3 times on different DataNodes}}

Benefits of blocks: (1) a file can be bigger than any single disk; (2) a fixed-size unit simplifies storage management; (3) blocks fit replication — each block is copied to 3 separate machines for fault tolerance.

NameNode and DataNodes

🗣 In plain words
A library: the NameNode is the catalogue (which book is made of which pages, on which shelf); DataNodes are the shelves holding the pages.
  • Master–worker pattern. The NameNode (master) manages the namespace — the file tree and metadata — stored on disk as the namespace image and the edit log. It learns block locations from DataNode reports.
  • DataNodes (workers) are the workhorses: store and retrieve blocks when told, and report their block lists to the NameNode periodically.
  • Without the NameNode the file system is unusable — all files would be lost. So it is protected two ways: (1) write its metadata to several file systems at once (local disk + remote NFS, synchronous and atomic); (2) run a Secondary NameNode that periodically merges the namespace image with the edit log so the log doesn't grow too large; it keeps a copy of the merged image for recovery.
{{fig:u2_arch|✏️ must-draw · HDFS architecture}} {{fig:u2_snn|Checkpointing by the Secondary NameNode}}
⚠️ Trap
The Secondary NameNode is NOT a backup NameNode — it only checkpoints. Automatic takeover is done by the Standby NameNode in High Availability (next section).

2.5HDFS Federation and High Availability@@b5@@

Federation — solves scaling. The NameNode holds every file and block in memory, so memory limits cluster size. HDFS Federation (Hadoop 2.x) adds NameNodes, each managing part of the namespace (e.g., one for /user, one for /share). Each manages a namespace volume = metadata + a block pool. Volumes are independent: NameNodes don't talk to each other, and one failing doesn't affect the others.

{{fig:u2_fed|HDFS Federation}}

High Availability — solves the single point of failure. Backups and checkpoints prevent data loss, but the NameNode is still a single point of failure (SPOF): if it dies, nobody can read, write or list files. Starting a new one means (i) loading the namespace image, (ii) replaying the edit log, (iii) receiving enough block reports to leave safe mode — 30+ minutes on big clusters.

Hadoop 2 HA uses an active–standby pair; the standby takes over without significant interruption. Needed changes: (1) shared edit log on highly available storage; (2) DataNodes send block reports to both NameNodes; (3) clients handle failover transparently; (4) the standby takes the checkpoints (replacing the Secondary NameNode).

{{fig:u2_ha|Active and standby NameNodes}}

2.6Anatomy of a file read and a file write@@b6@@

File read — 6 steps

🗣 In plain words
Ask the NameNode where the blocks are, then read each block directly from the nearest DataNode, one after another. Data never passes through the NameNode.
{{fig:u2_read|✏️ must-draw · A client reading data from HDFS}}
  1. Client calls open() on DistributedFileSystem.
  2. It calls the NameNode by RPC for the locations of the first blocks; for each block, DataNodes are returned sorted by closeness. The client gets an FSDataInputStream (wrapping a DFSInputStream).
  3. Client calls read(); the stream connects to the closest DataNode for the first block.
  4. Data is streamed back as the client keeps calling read().
  5. At the end of a block, it closes that connection and finds the best DataNode for the next block (asking the NameNode for more locations as needed).
  6. Client calls close().

Failures: if a DataNode fails, try the next closest one and remember the bad node; data is checked with checksums — a corrupt block is read from another replica and reported to the NameNode. Why this design is good: clients go straight to DataNodes, so traffic is spread out and the NameNode only answers quick location lookups.

File write — 7 steps

🗣 In plain words
Ask the NameNode to create the file, then push data in packets down a chain of 3 DataNodes; each saves and passes it on, and acknowledgements come back up.
{{fig:u2_write|✏️ must-draw · A client writing data to HDFS}}
  1. Client calls create() on DistributedFileSystem.
  2. RPC to the NameNode to create the file (no blocks yet). It checks the file doesn't exist and the client has permission, else IOException. Client gets an FSDataOutputStream.
  3. As the client writes, data is split into packets placed in the data queue. The DataStreamer asks the NameNode for new blocks and a list of DataNodes, which form a pipeline (3 nodes for replication 3).
  4. Packets go to DataNode 1, which stores and forwards to DataNode 2, then DataNode 3.
  5. Packets wait in the ack queue until all DataNodes acknowledge them.
  6. Client calls close() — remaining packets are flushed and acks awaited.
  7. The NameNode is told the file is complete.

If a DataNode fails during writing: the pipeline is closed; packets in the ack queue go back to the front of the data queue; the block on the good nodes gets a new identity (so the partial block on the failed node is deleted later); the failed node is removed and a new pipeline is built from the two good nodes. The NameNode later adds the missing replica.

2.7MapReduce workflows and unit tests@@b7@@

When a problem gets harder, use more MapReduce jobs, not more complex ones (or a higher-level tool: Pig, Hive, Cascading, Crunch, Spark). Example: mean maximum temperature per station per day needs two jobs — Job 1 finds the max per (station, date); Job 2 drops the year and averages per (station, day-month): (25 + 27 + 29) ÷ 3 = 27 °C.

{{fig:u2_jobs|Breaking a complex problem into two MapReduce jobs}}

Jobs in a linear chain are run one after another with JobClient.runJob() (a failure throws IOException and stops the chain). Jobs forming a DAG (directed acyclic graph) are managed by JobControl: it stores jobs, records dependencies, runs them in order, monitors progress, reports status, and skips dependents if a job fails.

MRUnit is a testing library (used with JUnit) that feeds known input to a mapper or reducer and checks the output; a mismatch fails the test. MapDriver tests the mapper (weather record → (1950, −11)); ReduceDriver tests the reducer (1950, [10, 5] → (1950, 10)); the local job runner tests the whole job on a small file.

2.8How a job runs: classic MapReduce and YARN@@b8@@

A job is started by one call — submit() or waitForCompletion(). The property mapreduce.framework.name chooses how it runs: local (whole job in one JVM, for testing), classic (MapReduce 1: JobTracker + TaskTrackers), or yarn (MapReduce 2).

Classic MapReduce (MR1)

Four entities: the client (submits) · the JobTracker (coordinates the job) · TaskTrackers (run the tasks) · the distributed file system (shares job files).

{{fig:u2_mr1|✏️ must-draw · Job run in classic MapReduce (steps 1–10)}}
  1. Submission (1–4): JobSubmitter gets a new job ID from the JobTracker; checks the output directory (must not exist) and computes input splits; copies the job JAR (high replication), config and splits to the shared FS; calls submitJob().
  2. Initialisation (5–6): job goes into an internal queue; the scheduler creates the job object, retrieves the splits and makes one map task per split (reduce count from mapred.reduce.tasks).
  3. Assignment (7): TaskTrackers send heartbeats — "I'm alive, I'm free" — and the JobTracker replies with a task.
  4. Execution (8–10): the TaskTracker copies the JAR locally (plus distributed-cache files), and a TaskRunner launches a new JVM for each task, so bugs in user code can't crash the TaskTracker.

YARN (MapReduce 2)

🗣 In plain words
In MR1 the JobTracker did two jobs — managing cluster resources and babysitting every task — and choked at around 4,000 nodes. YARN splits it: one ResourceManager for the cluster, plus an ApplicationMaster for each job.
{{fig:u2_yarnsplit|YARN splits the JobTracker into two daemons}}

YARN = Yet Another Resource Negotiator (designed at Yahoo!, 2010). Five entities: client · ResourceManager (allocates cluster resources) · NodeManagers (launch and monitor containers) · MRAppMaster (coordinates the job's tasks; runs in a container) · distributed file system.

{{fig:u2_yarn|✏️ must-draw · Job run on YARN (steps 1–11)}}
  1. Submission (1–4): get a new application ID from the ResourceManager; check output; compute splits; copy resources; submitApplication().
  2. Initialisation (5a, 5b, 6, 7): the scheduler allocates a container and the RM launches the MRAppMaster in it via a NodeManager; the AM creates bookkeeping objects and retrieves the splits.
  3. Assignment (8): the AM requests containers from the RM — map tasks first (higher priority); reduce tasks only after 5% of maps finish. (Tiny jobs may run as an uber task inside the AM.)
  4. Execution (9a, 9b, 10, 11): the AM asks a NodeManager to start the container; YarnChild localises the JAR/config, then runs the map or reduce task. Tasks report progress to the AM.

Job scheduling

{{fig:u2_sched|FIFO vs Fair vs Capacity scheduling}}
  • FIFO — default in MR1; one queue, first come first served.
  • Fair Scheduler — gives every user a fair share over time. A lone job gets the whole cluster; as jobs arrive, slots are shared so short jobs finish even while long jobs run. Jobs go in pools (one per user by default). Supports preemption: if a pool is starved, tasks in over-capacity pools are killed to free slots.
  • Capacity Scheduler — the cluster is split into queues (can be hierarchical), each with a fixed capacity; inside each queue jobs run FIFO (with priorities) — like a separate mini-cluster per team.
  • Preemption = forcefully taking resources from one job and giving them to a higher-priority one.
🧠 Memory trick
Fair → Pools ("Friends Play fair"); Capacity → Queues ("Companies Queue up").

2.10Shuffle and sort@@b10@@

Definition

MapReduce guarantees that the input to every reducer is sorted by key. The process of performing this sort and transferring map outputs to reducers is the shuffle — "the heart of MapReduce, where the magic happens".

{{fig:u2_shuffle|✏️ must-draw · Shuffle and sort}}
Map side
  1. Output goes to a circular memory buffer of 100 MB.
  2. At 80% full, a background thread spills to disk (round-robin into mapred.local.dir); the map blocks only if the buffer fills completely.
  3. Before writing, data is partitioned by destination reducer.
  4. Each partition is sorted by key in memory; the combiner (if any) runs on it.
  5. Several spill files are merged into one partitioned, sorted output file (optionally compressed).
  6. Partitions are served to reducers over HTTP.
Reduce side
  1. Copy phase — starts copying each map's output as soon as that map finishes, using 5 copier threads.
  2. Small outputs go to memory, large ones to disk; buffers are merged and spilled, and background threads merge disk files.
  3. Sort phase (really a merge phase — sorting was done map-side) — merges outputs in rounds, keeping order.
  4. Reduce phase — the last merge feeds the reduce function directly; it runs once per key; output goes to HDFS.
🧠 Memory trick
Map side: "Big Spills Please Sweep, Clean, Mop" — Buffer, Spill, Partition, Sort, Combine, Merge. Reduce side: Copy → Merge → Reduce.
