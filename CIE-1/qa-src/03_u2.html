Q19.What is Hadoop? Name its core components.2M

Hadoop is an open-source framework, written in Java (by Doug Cutting and Mike Cafarella), that allows us to store and process large data sets in a parallel and distributed manner. Core components: HDFS (storage layer), MapReduce (processing layer) and YARN (resource management layer), plus Hadoop Common utilities.

Q20.What is data locality optimisation?2M

Hadoop tries to run each map task on the node where its input data (HDFS block) already resides, so that valuable cluster network bandwidth is not used. If that node is busy, it uses a node in the same rack (rack-local); only rarely a node in another rack (off-rack, with an inter-rack transfer).

Q21.What is the default HDFS block size? Why is it so large?2M

The default HDFS block size is 128 MB (64 MB in older versions), much larger than a disk block (512 bytes). Large blocks keep the time spent seeking small compared to the time spent transferring data, and they reduce the metadata the NameNode keeps in memory. A file smaller than a block uses only its actual size on disk.

Q22.What is the role of the Secondary NameNode?2M

The Secondary NameNode periodically merges the namespace image with the edit log (checkpointing) so the edit log does not grow too large. It runs on a separate machine and keeps a copy of the merged image that can be used if the NameNode fails. It is not a backup NameNode and cannot take over automatically.

Q23.What is MRUnit?2M

MRUnit is a testing library for MapReduce, used with JUnit, that passes known inputs to a mapper or reducer and checks that the outputs are as expected. MapDriver tests a mapper (e.g., weather record → (1950, −11)) and ReduceDriver tests a reducer (e.g., (1950, [10, 5]) → (1950, 10)); a mismatch fails the test.

Q24.Expand YARN. Why was it introduced?2M

YARN = Yet Another Resource Negotiator (MapReduce 2). Classic MapReduce hit scalability bottlenecks around 4,000 nodes because the single JobTracker did both job scheduling and task monitoring. YARN splits these into a ResourceManager (cluster resources) and a per-application ApplicationMaster (job lifecycle).

Q25.Explain the design of HDFS.3M

HDFS is a file system designed for storing very large files with streaming data access patterns, running on clusters of commodity hardware.

  1. Very large files — hundreds of MB, GB or TB; clusters store petabytes.
  2. Streaming data access — built on write-once, read-many-times; reading the whole dataset quickly matters more than the latency of the first record.
  3. Commodity hardware — runs on cheap hardware where node failure is common, and keeps working without noticeable interruption.

Not suited for: low-latency access (use HBase), lots of small files (NameNode memory), multiple writers / arbitrary modifications.

Q27.What is HDFS Federation?3M
  1. The NameNode keeps every file and block reference in memory, so on very large clusters memory limits scaling.
  2. HDFS Federation (Hadoop 2.x) lets a cluster scale by adding NameNodes, each managing a portion of the namespace — e.g., one for /user, another for /share.
  3. Each NameNode manages a namespace volume (metadata + a block pool). Volumes are independent: NameNodes don't communicate, and one failing doesn't affect the others.
Q28.Explain HDFS High Availability.3M
  1. Problem: the NameNode is a single point of failure; a cold restart (load namespace image, replay edit log, collect block reports to leave safe mode) can take 30+ minutes.
  2. Solution: a pair of NameNodes in active–standby configuration; if the active fails, the standby takes over without significant interruption.
  3. Changes needed: a shared edit log on highly available storage; DataNodes send block reports to both NameNodes; clients handle failover transparently; the standby takes periodic checkpoints (replacing the Secondary NameNode).

Q30.Explain the failure modes in classic MapReduce.3M
  1. Task failure — user code throws a runtime exception, or the child JVM exits suddenly; the TaskTracker marks the task attempt as failed and frees the slot (Streaming: non-zero exit code).
  2. TaskTracker failure — it crashes or runs slowly and stops sending heartbeats; the JobTracker removes it from its pool. It can be blacklisted if more than four tasks of a job fail on it and its faults are well above the average.
  3. JobTracker failure — the most serious: it is a single point of failure with no recovery mechanism, so the job fails (fixed in YARN).

Q31.Explain how MapReduce finds the maximum temperature for each year, with a data-flow diagram.5M

MapReduce breaks processing into two phases — map and reduce — each with key–value pairs as input and output; the programmer writes the map and reduce functions. The NCDC weather dataset is semi-structured and record-oriented (temperature stored as °C × 10, 9999 = missing).

{{fig:u2_flow|MapReduce logical data flow}}
  1. Input: each line is given to the mapper as (key = line offset, value = record).
  2. Map: the mapper extracts the year and air temperature, filters out missing/bad readings and emits (year, temperature): (1950, 0), (1950, 22), (1950, −11), (1949, 111), (1949, 78).
  3. Shuffle & sort: the framework groups and sorts values by key: (1949, [111, 78]), (1950, [0, 22, −11]).
  4. Reduce: the reducer iterates through each list and picks the maximum: (1949, 111), (1950, 22).
  5. Java: Mapper<LongWritable, Text, Text, IntWritable>, Reducer<Text, IntWritable, Text, IntWritable>, and a Driver that sets input/output paths, mapper/reducer classes and output types, then calls waitForCompletion(). Output file: part-r-00000.

Q32.Explain the anatomy of a file read in HDFS.5M
{{fig:u2_read|A client reading data from HDFS}}
  1. The client opens the file by calling open() on the FileSystem object, an instance of DistributedFileSystem.
  2. DistributedFileSystem calls the NameNode using RPC to get the locations of the first few blocks; for each block, the NameNode returns the DataNodes holding a copy, sorted by proximity to the client. It returns an FSDataInputStream (wrapping a DFSInputStream).
  3. The client calls read(); DFSInputStream connects to the closest DataNode for the first block.
  4. Data is streamed from the DataNode to the client as it repeatedly calls read().
  5. At the end of a block, DFSInputStream closes the connection and finds the best DataNode for the next block, asking the NameNode for further block locations as needed.
  6. When finished, the client calls close().

Failure handling: if a DataNode fails, the stream tries the next closest one and remembers the failed node; it verifies checksums and, on a corrupt block, reads another replica and reports the corrupt block to the NameNode. The client reads directly from DataNodes, so the NameNode is not a bottleneck.

Marks split: diagram 1.5 · six steps 3 · failure handling 0.5
Q33.Explain the anatomy of a file write in HDFS.5M
{{fig:u2_write|A client writing data to HDFS}}
  1. The client creates the file by calling create() on DistributedFileSystem.
  2. DistributedFileSystem makes an RPC call to the NameNode to create a new file with no blocks. The NameNode checks that the file doesn't already exist and the client has permission; otherwise an IOException is thrown. An FSDataOutputStream is returned.
  3. As the client writes, DFSOutputStream splits data into packets placed in the data queue. The DataStreamer asks the NameNode to allocate new blocks on suitable DataNodes, which form a pipeline (three nodes for replication 3).
  4. The DataStreamer sends packets to the first DataNode, which stores and forwards them to the second, which forwards to the third.
  5. Packets wait in the ack queue and are removed only when acknowledged by all DataNodes in the pipeline.
  6. The client calls close(), which flushes remaining packets and waits for acknowledgements…
  7. …before telling the NameNode the file is complete.

If a DataNode fails: the pipeline is closed, ack-queue packets are put back at the front of the data queue, the current block on good nodes gets a new identity (so the partial block is deleted later), the failed node is removed and the pipeline is rebuilt from the remaining good DataNodes.

Q34.Explain how a MapReduce job runs in classic MapReduce (MapReduce 1).5M

Four independent entities: the client (submits the job), the JobTracker (coordinates the job run), the TaskTrackers (run the tasks) and the distributed file system (shares job files).

{{fig:u2_mr1|How Hadoop runs a MapReduce job using the classic framework}}
  1. Job submission (1–4): submit() creates a JobSubmitter, which asks the JobTracker for a new job ID, checks the output specification (error if the output directory exists), computes input splits, copies the job JAR (with high replication), configuration and splits to the shared file system, and calls submitJob().
  2. Job initialisation (5–6): the job goes into an internal queue; the scheduler creates an object to track it, retrieves the input splits and creates one map task per split; the number of reduce tasks comes from mapred.reduce.tasks.
  3. Task assignment (7): TaskTrackers send periodic heartbeats saying they are alive and ready; the JobTracker allocates a task in the heartbeat reply.
  4. Task execution (8–10): the TaskTracker localises the job JAR and distributed-cache files, creates a working directory, and a TaskRunner launches a new JVM to run each map or reduce task, so bugs in user code don't affect the TaskTracker.

Q35.Explain how a MapReduce job runs on YARN. How is it different from classic MapReduce?5M

YARN splits the JobTracker's work into a ResourceManager and a per-job ApplicationMaster. Five entities: client, YARN ResourceManager (allocates compute resources), NodeManagers (launch and monitor containers), MRAppMaster (coordinates the job's tasks) and the distributed file system.

{{fig:u2_yarn|How Hadoop runs a MapReduce job using YARN}}
  1. Submission (1–4): get a new application ID from the ResourceManager, check output, compute splits, copy resources to the shared FS, call submitApplication().
  2. Initialisation (5a–7): the scheduler allocates a container and the RM launches the MRAppMaster there via a NodeManager; the AM creates bookkeeping objects and retrieves the input splits.
  3. Task assignment (8): the AM requests containers from the RM — map tasks first, reduce tasks after 5% of maps complete.
  4. Task execution (9a–11): the AM asks the NodeManager to start the container; YarnChild localises the resources and runs the task.

Difference: MR1 has 4 entities and a JobTracker that does both scheduling and monitoring (bottleneck at ~4,000 nodes, single point of failure); YARN has 5 entities, separates resource management from job monitoring, uses flexible containers instead of fixed slots, and scales much further.

Q36.Explain shuffle and sort in MapReduce.5M

MapReduce guarantees that the input to every reducer is sorted by key. The process of performing this sort and transferring map outputs to the reducers is called the shuffle — the heart of MapReduce.

{{fig:u2_shuffle|Shuffle and sort in MapReduce}}

Map side:

  1. Each map task writes output to a circular memory buffer of 100 MB.
  2. When it reaches the threshold (80%), a background thread spills it to disk (round-robin into mapred.local.dir).
  3. Before writing, data is partitioned by the reducer it will go to; within each partition it is sorted by key in memory and the combiner (if any) runs.
  4. Spill files are merged into one partitioned, sorted output file (optionally compressed) and served to reducers over HTTP.

Reduce side:

  1. Copy phase — the reducer copies its partition from each map as soon as that map finishes, using 5 copier threads.
  2. Sort (merge) phase — map outputs are merged in rounds, keeping the sort order.
  3. Reduce phase — the reduce function is called once per key; output is written to HDFS.
